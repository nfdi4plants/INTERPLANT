# Portal Mapping Spec

**Scope:** How an INTERPLANT L2 record is mapped onto the Earth Data Portal's internal `DocumentSchema.json`. This spec governs the mapper the OAI-PMH endpoint will use in production.

**Authoritative reference mapper:** [`scripts/portal_mapper.py`](../../scripts/portal_mapper.py).

**Pinned upstream schema:** [`schemas/portal-document-schema.json`](schemas/portal-document-schema.json) (snapshot from `gitlab.awi.de/software-engineering/index/de.awi.index/DocumentSchema.json`).

**Canonical fixture:** [`examples/portal-document-chlamy.json`](examples/portal-document-chlamy.json) — produced by applying `portal_mapper.map_record` to `record-complete.json`.

## 1. Field-by-field mapping

| L2 record field | Portal field | Transform |
|---|---|---|
| `id` | `id` | copy |
| `properties.uniqueId` | `uniqueId` | copy |
| `properties.doi` | `identifiers[]` | wrap as `{type:"doi", id:<doi>}` (omit if no DOI) |
| `properties.title` | `title` | copy |
| `properties.description` | `description` | copy |
| `properties.created` | `date` | copy |
| `time.interval` | `temporalCoverage` | wrap as `{lower, upper}` when both bounds non-null; omit otherwise |
| `geometry` | `geometry` | copy; omit key when null |
| `properties.keywords` | `keywords.topics[]` | wrap each as `{type:"topic", name, description:""}` |
| `properties.omics_domains` | `keywords.omics[]` | wrap each as `{type:"omics", name, description:""}` |
| `properties.experiment_context` | `keywords.contexts[]` | wrap as single `{type:"context", name, description:""}` |
| `properties.organism` | `keywords.organisms[]` | wrap each as `{type:"organism", name, description:""}` |
| `properties.project` | `keywords.projects[]` | wrap each as `{type:"project", name, description:""}` |
| `properties.contacts[].role` | `persons.<role>[]` | one person per role bucket; ORCID moved into `identifiers.orcid` |
| `properties.creators` | `persons.author[]` | append to the `author` bucket |
| `properties.assays[]` | `devices[]` | each assay → `{id, name: instrument_name || domain, type:"instrument", metadata:{domain}}` |
| `properties.studies[]` | `events[]` | each study → `{id, type:"study", begin, end, geometry}` (geometry only when record-level geometry exists) |
| `properties.arc_source_uri` | `resources[]` | `{title:"ARC source", type:"relation", uri, metadata:{relationType:"source"}}` |
| `properties.publications[]` | `resources[]` | `{title: pub.title, type:"relation", uri:"https://doi.org/<doi>", metadata:{relationType:"isDocumentedBy"}}` |
| constant | `genericType` | `"data"` |
| constant | `platforms[]` | always `[]` — plant ARCs are not on research vessels |
| constant | `expeditions[]` | always `[]` |
| `properties.harvester_version` | `version` | copy |
| `properties.record_quality` | `metadata.record_quality` | copy into free metadata bag |
| `properties.harvested_at` | `metadata.harvested_at` | copy into free metadata bag |

## 2. Identifier strategy

- `uniqueId` is a UUIDv5 generated by the harvester from `arc_source_uri`. Stable, derivable.
- `id` is the INTERPLANT record slug; unique within our catalog but may collide across providers. The portal treats `uniqueId` as the authoritative identifier.
- Never construct fake DOIs. ARCs without a DOI omit `identifiers[]` entries of type `doi`.

## 3. Vocabulary alignment

- **ORCID** — required for every person record that has one. The harvester preserves 0-padded ORCIDs verbatim (`0000-0002-…`).
- **ROR** — required for organisations when known. Not implemented in v1; placeholder only (see open question #5).
- Keyword `type` strings in nested arrays are stable identifiers: `topic`, `omics`, `context`, `organism`, `project`. Downstream consumers filter on these.

## 4. Null / missing handling

- Geometry: null → omit the `geometry` key entirely in the mapped document (portal schema accepts absence).
- Time: any `null` in `time.interval` → omit `temporalCoverage`.
- DOI: absent → omit the corresponding `identifiers[]` entry.
- Persons with no ORCID: emit `identifiers: {}` (empty object), not `null`.

## 5. Determinism

The reference mapper is deterministic: identical input produces byte-identical output. Sort orders are stable:

- `identifiers[]` with DOI first when present. v1 emits only DOI; future identifier types (ROR, etc.) will append after the DOI entry.
- `keywords.*[]` in source-list order.
- `persons.<role>[]` in source-list order.
- `devices[]` in `assays[]` order.
- `events[]` in `studies[]` order.
- `resources[]` in source-first then publication-order.

Tests pin the canonical fixture; production mappers must match.

## 6. Validation

`tests/specs/test_portal_mapping.py`:
1. `examples/portal-document-chlamy.json` validates against the pinned portal schema.
2. Running the reference mapper on `record-complete.json` produces output byte-equal to the committed fixture.

Both must pass in CI.

## 7. Out of scope (for now)

- `parameters[]` — the portal's sensor-parameter concept doesn't map cleanly to ARC assays; omitted from v1 mapping.
- `states[]` — no ARC-side signal to drive this; omitted.
- `order` — no cross-record ordering; omitted.
- `source` — fulltext pass-through; deferred.
- `organisations` — requires ROR-resolved affiliations; deferred to v2 (see § 3 and open question #5).
- Per-study event geometry — `events[]` carries record-level geometry only. Field-trial ARCs with multiple studies at different sites collapse to one geometry in v1; per-study geometry is a v2 enhancement.
